## Correctness and integration risks

1. **Assignment time and snapshot are not driving relevance inputs.** `neighborhoodRelevanceEngine.js:188` loads subject and candidate characteristics from the latest parcel/account rows. `loadCandidateSales` (`:349–370`) uses `CURRENT_DATE - 36 months`, no upper effective-date bound, primary account only, and returns only price/date (discarding canonical transaction IDs). Use a scoped source adapter with explicit effective date, observation convention and verified additional-parcel allocation. Preserve transaction identity and deduplicate once per transaction, not per parcel.
2. **Property fallback is a candidate, not assignment acceptance.** Latest boundary (`neighborhoodBoundaryEngine.js:760–787`) and relevance (`neighborhoodRelevanceEngine.js:998–1024`) can fall back to `scope_key='property'`. v1 must label that fallback unaccepted and bind any attachment to organization/case/snapshot/effective date. Do not silently reuse a current account result for a historical assignment.
3. **Age/missingness errors exist in both runtime consumers.** Server `finiteValues` (`neighborhoodRelevanceEngine.js:654`) and frontend `neighborhoodPocketSelection.ts` use numeric conversion before excluding missing values. Null can become zero. Server lines 736/744 and frontend lines 108/116 place year-built into age summaries. Provide year-built, age at effective date and age at sale as distinct measurements; reject impossible years.
4. **Median is not a predominant estimate.** `useNeighborhoodProfile.ts:153–162` and `NeighborhoodCharacteristicsContent.tsx:794–817` map medians into predominant fields. A v1 result should explicitly name a median and either expose a supported predominant estimator/method or leave predominant unsupported. Do not relabel assessed values as verified market prices of unsold properties.
5. **Repeated sales inflate apparent coverage and reliability.** Server `neighborhoodRelevanceEngine.js:758` and frontend `neighborhoodPocketSelection.ts:130` divide transaction count by parcel count. Separate transactions, unique sold properties, eligible stock coverage, completeness, similarity, uncertainty and sample support. Low price dispersion is not by itself accuracy or reliability.
6. **Geographic protection bypasses competitive eligibility.** `applyLandUsePrerequisite` (`neighborhoodRelevanceEngine.js:479–485`) skips mismatches for same-subject-neighborhood parcels; contiguous classification (`:443`) clears their excluded state. Keep these parcels visible in geographic context but require independent housing/transaction eligibility for competitive statistics. Matching subdivision names must not erase phase/type differences.
7. **Cache/hash inputs are incomplete.** Relevance signature (`:963–976`) omits GLA, housing category, subdivision/neighborhood identity, subject snapshot and effective date despite those affecting selection. Profile execution key (`neighborhoodProfileExecution.js:162`) has date/geometry/context but no authorized assignment/snapshot/source revision. Land-use key (`neighborhoodLandUse.js:781`) is only account + geometry and profile age uses current year (`:887`). Build a canonical complete signature, not a new partial browser string.
8. **Local and live land-use overlays disagree on overlap accounting.** Live clipping dissolves per category and subtracts prior categories (`neighborhoodLandUse.js:370–393`). Local mirror clipping sums each parcel (`:484–494`), so overlapping/stacked tax parcels may be counted twice and apparent overlap is zero because covered/raw sums are identical. v1 must resolve overlaps and report full-area versus parcel-covered denominators, rights-of-way/uncovered area and classification uncertainty. Do not run land-use totals on the narrowed similarity population.
9. **Road linework is not yet a validated boundary graph.** `orderedRoadPoints` (`neighborhoodBoundaryEngine.js:78`) flattens/sorts vertices and samples at most 40 per side; `buildRoadwayBoundary` (`:163–173`) concatenates and closes them. Source gaps can be bridged by invented straight segments. `propertyContextSync.js:1107–1108` hashes snapped part endpoints without noding interior intersections. Reuse raw roads but build a versioned planar cell topology; keep travel connectivity separate.
10. **Current pockets are provisional and membership-dependent.** `neighborhoodRelevanceEngine.js:601–628` groups recorded identity or deterministic map cells and uses minimum parcel ID for pocket ID. This is not a durable phase registry and IDs can change with membership. Adjacency query (`:376–400`) stops at 100,000 edges without a truncation diagnostic. Stable pocket revisions and explicit incomplete status are required.
11. **UI currently owns analytical truth twice.** `NeighborhoodCharacteristicsContent.tsx:235/242` calls browser override/recommendation algorithms; `:794` writes derived statistics into assignment fields; `:933–937` recalculates on pocket clicks. Replace these calculations with a server preview/review result while retaining immediate selection affordances, stale-response guards, appraiser ownership and saved override provenance.
12. **Existing shared completion requires a Custom source.** `appraisalCompletionAdapter.js:459` rejects non-Custom source reports; loader lines 604–618 searches for a same-case/snapshot Custom file and fails if none exists. Preserve this old contract while adding a workflow-neutral assessment source for UAD-only reports. The existing case/snapshot checks (`:446–457`) and target-specific source digest (`:511–523`) must remain; nest the immutable assessment digest rather than replacing target guards.
13. **Read paths still ensure mutable schemas.** Boundary/relevance GET handlers themselves retrieve rather than create analysis jobs, but latest getters call schema-ensure helpers (`neighborhoodBoundaryEngine.js:771`, `neighborhoodRelevanceEngine.js:1009`). Avoid adding v1 DDL/registry writes/jobs to GET paths. Schema initialization belongs in the separately coordinated migration lifecycle.
