# Neighborhood cached-source reader checkpoint

This next layer depends on the accepted assessment contract and persistence in PRs #611/#613. It is not wired to report reads, generation routes, schedulers, or either report consumer. There are no new migrations or provider calls in this slice. It does not certify live source coverage or complete the neighborhood feature.

## Reader ownership and exact evidence

`createNeighborhoodCachedSourceReader(pool, { access }).capture(request)` requires an original server-composition authority plus its paired, single-use selection and licensed-market tokens. `createNeighborhoodCachedReadAccess` requires four trusted services: exact assignment authorization, immutable server selection resolution, explicit licensed-market policy, and identity-only one-hop transaction closure resolution. There is no unrestricted account-ID mint, caller-injected verifier or assignment-only fallback. This is `local-capture-v2`; earlier v1 captures did not supply this authorization evidence.

`access.prepare(auth, { target, selection_reference, observation_period, knowledge_cutoff })` accepts references, not browser-supplied account IDs, scope or digests. Authenticated owner services supply canonical report/workflow/organization/case/snapshot/subject/date context and the server-owned selection. Pass its request and original tokens, with trusted authentication context, to `capture`. Private WeakMaps bind the original authority and tokens to the exact actor, target, scope, dates, selection/source versions, licensed-policy decision and closure. Copies, other issuers, changed scope/IDs/dates, replay and expiry are rejected before the cache connection. The bounded lifetime starts before the first asynchronous authorization callback.

Every selected or directly associated account receives an original `authorizePublicCadastralCatalogRead` grant, verified through Cyber's runtime-unforgeable assertion. Generic exact-organization/workflow read permission remains necessary but does not grant MLS access. A mandatory market policy must explicitly approve all source rows in the declared source-record, canonical-sale and parcel-association classes for that selection/organization/workflow. The decision ID and policy revision are bound to the request. Its purpose covers all available event dates for seeded transactions: the observation period is analytical, not a licensed-read filter. Partial source/date entitlement must deny; this reader has no licensed-row filtering mode.

Only after the market decision may the trusted resolver load association identities. `validateCachedTransactionClosure` derives a bounded one-hop closure: sources must intersect selected IDs through primary, stored-sale or additional-parcel links; legacy sales must be selected directly. Closure-only accounts never seed another transaction, add stock members or authorize private assignment overlays. All linked-parcel metadata survives, including unresolved/null identities, without claiming complete real-world membership. The 50,000-account cap covers selected and closure accounts together; identity metadata is separately capped at100,000 rows/8MB. No callback may echo browser IDs or the reader's own result as its expected closure.

The reader rechecks the frozen identity closure in its repeatable-read snapshot before full price/MLS projections. Added, missing, reassociated or changed-identity records produce atomic incompleteness without market data return. Only original selected IDs appear in cadastral/account SQL and the statistical selection manifest. The relational scope/date check is additional integrity, not authorization. Production owner/license/selection resolver wiring is still pending; synthetic test callbacks prove boundary behavior, not actual dataset entitlement. No route or report activation is included.

This is the **selected-account evidence reader**, not yet the spatial discovery engine. It does not choose three-mile bounds, resolve account aliases, find developments, certify housing eligibility, or select comparable transactions. Every parcel feature with an exact selected `account_id` is retained; no smallest-parcel or LOWPARCELID fallback silently defines the subject.

One checked-out client reads all tables in a `REPEATABLE READ READ ONLY` transaction. Queries use fixed, column-checked projections with exact bigint IDs as strings. Source transactions are discovered through source-primary, additional-parcel, and stored-sale account associations. Every link for those source identities is then read, including unselected accounts, unresolved/null accounts and secondary positions. Separate legacy sales and source-only records survive. There is no 30-sale target, per-property sale limit, positive-price filter, relative/current-date cohort, enriched-view fallback, or price/date duplicate heuristic. The explicit event window is retained for the later eligibility stage; the input capture includes touched history so conflicting and unknown dates are not hidden.

Raw source and canonical price/date/account claims stay separate. The four pure row mappers preserve their complete allowlisted projection, mapped values, mapping/content version and capability gaps. They do not turn current cache rows into historical facts, GIS land-use categories into verified housing subtypes, source closed-sale labels into verified consideration, or a complete SQL link scan into full real-world parcel membership. Source identity hashes are retained under their original names; the capture hashes exact retained content separately.

GIS state and all selected originating sync runs come from the same database snapshot. Running, failed, missing or inconsistent completion evidence prevents usable capture publication. Unchanged parcels from earlier completed incremental runs are allowed; selecting only the latest run would lose them. Absent/unsupported source tables and missing selected parcel coverage also produce `incomplete`, never complete empty statistics. An explicit historical knowledge cutoff requires previously retained evidence; this reader does not try to reconstruct overwritten rows by filtering update timestamps.

## Bounds and failure behavior

Default ceilings are 100,000 aggregate retained records (including the selected-account manifest and identity preflight), 30 MB of retained row payloads, 64 KB per SQL projection row, 250 rows per page, and 50,000 selected accounts. These are safety limits, not cohort-size targets. Query pages use overflow sentinels and deterministic outer ordering; complete scans exhaust every page. Detail joins are themselves bounded and reject duplicate/fan-out identities rather than relying only on expected indexes. SQL projects a null sentinel for oversized geometry/quality payloads before transferring them into Node. No arbitrary `raw_payload`, document text or private remarks are selected.

The read attempt has a 30-second wall-clock budget checked between queries, a five-second statement timeout, one-second lock timeout, ten-second idle-transaction timeout, and a three-second connection-acquisition timeout. The injected pool must retain ordinary connection limits. In-flight driver/server timeout latency can extend the wall-clock deadline; these are containment settings, not measured p95 latency. Connection failures are sanitized. Every attempted transaction is rolled back after failure; failed rollback destroys the connection. Late connection acquisition is released. No partial prefix becomes a usable population.

Hashing and bounded source chunk preparation happen after the read transaction closes. A `captured` result means this selected SQL envelope was captured, not that analytical eligibility or provider completeness is ready. Its assignment-private immutable chunks include the exact selection digest/members, query/column/mapping version, scope/dates, raw records, normalized claims and explicit unresolved capabilities. Downstream generation must consume these bytes, not re-query mutable mirrors. Persistence uses the existing publication path; this reader does not enqueue or publish by itself.

## Linework preparation

`prepareNeighborhoodLinework` independently validates a bounded cached road/alias capture, preserves exact part order, coordinates, names, source records, originating runs and repair limitations, and creates separate semantic and captured-evidence identities. It never connects same-name segments, snaps roads, nodes intersections, repairs geometry, builds cells or asserts travel access. Its strongest status is `ready_for_preprocessing`; `topology_validated` is always false. Invalid/incomplete/over-budget inputs produce no partial linework handoff.

The existing mutable endpoint-snapped road graph is not accepted as verified topology. Next work requires a concrete bounded road reader, source-preserving PostGIS noding, intersection/grade-separation distinctions, gap/overlap/sliver and polygon validity tests, immutable graph publication, and deterministic connected alternatives. Original pre-repair geometry absent from legacy mirrors remains unavailable, not reconstructed and relabeled as original.

## Verification and remaining gates

- Pure row mapping, source-reader transaction/pagination/failure tests, and graph-preparation tests run without a database or network. The reader test double checks the SQL contract but cannot prove query execution or MVCC behavior.
- `neighborhoodCachedSourceReader.integration.test.js` runs only through the accepted loopback GitHub CI child-database lifecycle. It uses canonical migrated assignment scope and explicitly identified source-projection fixtures. Tests exercise actual PostGIS geometry serialization, all discovery arms/links, bigint IDs, source-only and legacy records, one-snapshot behavior during concurrent mutation, absent/empty/populated sources, incomplete sync, budgets and scope denial. All clients close; no database is dropped by the test.
- The only CI command change appends that new test path to the existing `test:uad-migration` command. No workflow, security harness, environment names, credentials, applied migration or shared/live target changes.
- Actual PostgreSQL outcomes and exact commit/protected checks must be recorded after CI, not inferred from mocked tests. Representative `EXPLAIN (ANALYZE, BUFFERS)`, live data/coverage and latency remain unmeasured.

Still required: spatial discovery and complete source/version inventories; reviewed transaction/market/housing/history evidence; durable pockets/lineage/graph; research observation storage/adapters; server assessment orchestration; Custom atomic content-token/application integration; UAD owner mapping; shared consumer/report/security parity and appraiser pilots. Merges/deployment/provider activation follow the security owner's current release gates.

PostgreSQL references used when designing snapshot and pagination behavior: [Repeatable Read](https://www.postgresql.org/docs/current/transaction-iso.html) and [explicit ordering](https://www.postgresql.org/docs/17/queries-order.html). Those database guarantees do not make an in-progress source sync a completed provider version.
